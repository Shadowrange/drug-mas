## 1. Объект состояния графа

`GraphState` — `TypedDict, total=False` в `src/graph_state.py`.
Редьюсер только у `tool_calls` (`Annotated[list[ToolCall], operator.add]`),
у остальных полей — перезапись последним писателем.

| Поле | Тип | Пишет | Читает | Обязательно к моменту |
|---|---|---|---|---|
| `query` | `str` | вход графа | все | START |
| `scenario` | `str` (`lead_optimization` \| `target_to_hit` \| `insufficient_data_demo`) | supervisor | reporter, `build_result` | после supervisor |
| `task` | `dict` (см. ниже) | supervisor | data_agent, generator | после supervisor |
| `parent` | `Molecule \| None` | data_agent | generator, evaluator | до generator (для `lead_optimization` — не None) |
| `activities` | `list[dict]` | data_agent | data_agent (QSAR) | до generator |
| `n_activities` | `int` | data_agent | `check_data_sufficiency` | до роутера достаточности |
| `has_structure` | `bool` | data_agent | `check_data_sufficiency`, evaluator | до роутера достаточности |
| `receptor` | `dict \| None` `{"pdbqt_path": str, "center": tuple[float,float,float], "box": tuple}` | data_agent | evaluator (докинг) | до evaluator, если `has_structure` |
| `qsar` | `dict \| None` `{"model": object, "metrics": ModelMetrics}` | data_agent | evaluator | до evaluator (может быть None) |
| `missing` | `list[MissingData]` | data_agent (только из `check_data_sufficiency`) | роутер, reporter, `build_result` | после data_agent |
| `generated` | `list[Molecule]` | generator | evaluator | до evaluator, непустой |
| `candidates` | `list[Candidate]` | evaluator | verifier_node | до verifier, непустой |
| `verification` | `VerificationReport \| None` | verifier_node | роутер, reporter | после verifier |
| `rejected_all` | `list[Candidate]` | verifier_node | reporter | накапливается между кругами |
| `feedback` | `list[str]` | verifier_node | generator | перед вторым кругом |
| `loop` | `int` (старт 0) | только generator (`+= 1`) | роутер после verifier | всегда |
| `tool_calls` | `list[ToolCall]` (add) | **каждый** узел | verifier_node, reporter, фронт | до verifier — обязательно |
| `summary` | `str` | reporter | `build_result` | после reporter |
| `result` | `ScenarioResult \| None` | reporter (через `build_result`) | вызывающий код / `app.py` | END |

`task` (пишет только supervisor, дальше read-only):
```python
{"parent_name": str | None, "parent_smiles": str | None,
 "target_name": str | None, "target_uniprot": str | None,
 "target_chembl_id": str | None, "pdb_id": str | None,
 "objectives": list[str], "constraints": list[str], "plan": list[str]}
```

### Почему `tool_calls` критичен

`verify(candidates, tool_calls)` сверяет `Value.source` с журналом: если в source
есть подстрока из `SOURCE_REQUIRES_TOOL`, а успешного вызова соответствующего
инструмента в прогоне не было — кандидат ДИСКВАЛИФИЦИРУЕТСЯ целиком, не
«с примечанием». Отсюда три жёстких требования к реализации:

1. **`ToolCall.tool` — ровно одна из этих строк**, без префиксов и суффиксов:
   `pubchem_smiles`, `chembl_activities`, `uniprot_target`, `pdb_structure`,
   `qsar.predict`, `admet.profile`, `dock`, `interactions`.
   Любые другие вызовы (`chem.describe`, `generate.mutate`) логировать можно и нужно —
   верификатор их просто не сверяет.
2. **Лог пишется до возврата из узла**, в том же `return {"tool_calls": [...]}`.
   Узел, который сходил в ChEMBL и не залогировал вызов, обнуляет свои же данные.
3. **Неудачный вызов логируется с `ok=False` и текстом ошибки.** Это не косметика:
   `ok=False` означает, что значения с этим источником не пройдут, и значит
   их нельзя записывать вообще — вместо них `schemas.not_computed(...)`.

Три мины, на которые наступит реализация, если не предупредить:

- `parent` с `source="PubChem CID 5291"` требует успешного `pubchem_smiles`
  в ЭТОМ прогоне. Хардкод SMILES иматиниба в обход инструмента → весь прогон
  уходит в `unverifiable`. Либо реально звать (кэш греет), либо ставить
  `source="входные данные"`.
- `REQUIRED_FOR_RANKING = ("LogP", "QED", "SA_Score")`. Если `sascorer` из
  RDKit Contrib не поднялся, `chem.describe` вернёт `not_computed("SA_Score")`,
  и **все** кандидаты будут отсеяны по «Полнота данных». Проверить импорт
  до прогона — это блокер уровня докинга.
- `verify()` МУТИРУЕТ `c.filters` (`c.filters = c.filters + checks`). Один и тот
  же `Candidate` нельзя прогонять через `verify()` дважды — на втором круге
  фильтры удвоятся. Кандидаты второго круга должны быть новыми объектами,
  а выжившие с первого круга через verify повторно не прогоняются.

## 2. Узлы и рёбра

```
START -> supervisor -> data_agent -> route_sufficiency
                                       |-- missing     --> reporter -> END
                                       |-- ok          --> generator
generator -> evaluator -> verifier_node -> route_verify
                                       |-- passed      --> reporter -> END
                                       |-- retry       --> generator
                                       |-- exhausted   --> reporter -> END
```

Все узлы синхронные, сигнатура `def node(state: GraphState) -> dict`.
Возвращают ТОЛЬКО изменённые ключи. Исключений не поднимают: ошибка инструмента —
это `ToolCall(ok=False)` + `not_computed`, а не падение графа.

### supervisor
`(state) -> {"scenario", "task", "tool_calls"}`
Предусловие: `query`. 1 вызов LLM, JSON-режим. Инструментов не вызывает.
Если LLM вернула невалидный JSON — один retry, затем дефолт
`scenario="target_to_hit"`, `task` из regex-экстракции, и строка в `limitations`.

### data_agent
`(state) -> {"parent", "activities", "n_activities", "has_structure", "receptor", "qsar", "missing", "tool_calls"}`
Предусловие: `task`. 1 вызов LLM (план вызовов), затем детерминированное исполнение.
Порядок: `pubchem_smiles` / `uniprot_target` → `chembl_activities` → `pdb_structure`
→ `chem.describe(parent)` → `qsar.train` **только если** `n_activities >= Thresholds.min_qsar_train`.
Последним действием узла — `missing = check_data_sufficiency(n_activities, has_structure)`.
Узел НЕ решает, отказываться ли, он только считает.

### route_sufficiency (функция, не LLM)
`state["missing"] != [] -> "reporter"`, иначе `"generator"`.
Ветка отказа гарантирует `candidates=[]`: `build_result` при `missing` обнуляет
кандидатов сам, но generator на этой ветке и не запускается.

### generator
`(state) -> {"generated", "loop", "tool_calls"}`
Предусловие: `parent is not None`, `missing == []`, `loop < MAX_LOOPS`.
1 вызов LLM на круг — выдаёт ТОЛЬКО параметры (`backend`, `n`, подсказки), не SMILES.
Дальше `tools.generate.mutate(...)`. Фильтрует: валидность по `chem.parse`,
уникальность по каноническому SMILES, исключение SMILES, уже отсеянных в
`rejected_all`. `loop += 1` — **единственное место инкремента в графе**.
Если на выходе 0 новых молекул — возвращает `generated=[]`.

### evaluator
`(state) -> {"candidates", "tool_calls"}`
Предусловие: `generated` непустой. 1 вызов LLM, и только на первом круге
(`loop == 1`): выбирает шортлист на докинг и помечает риски текстом.
На втором круге шортлист берётся кодом (top-k по `score`) — экономия 1 вызова.
Порядок: `chem.run_all_filters` → `admet.profile` (если доступен) →
`qsar.predict` (если `qsar`) → `docking.dock` только по шортлисту (k ≤ 5) и только
если `receptor` есть. `score` считает КОД, детерминированной формулой по
посчитанным величинам; отсутствующая величина в `score` не входит и её вес
перераспределяется. `Candidate.rank` не ставит — ранг проставляет `build_result`.

### verifier_node (не LLM, обёртка над `verifier.verify`)
`(state) -> {"verification", "feedback", "rejected_all", "tool_calls"}`
Предусловие: `candidates` непустой, `tool_calls` заполнен.
```python
rep = verify(state["candidates"], state["tool_calls"])
rejected_all = dedupe_by_smiles(state.get("rejected_all", []) + rep.rejected)
```
`feedback = rep.feedback` (перезапись, не накопление: подсказки второго круга
актуальнее). `rep.unverifiable` не трогать — `build_result` сам положит их
в `limitations`.

## 2.5 Поправки к §1–2. Дописано 12.11, 02:00

§1 и §2 выше остаются в силе целиком. Ниже — четыре дыры, через которые
реализация даст пустой экран или потеряет данные, и поля, которых в §1 не хватает.

### Поправка 1. `generated == []` ведёт к пустому экрану

§2 разрешает generator вернуть `generated=[]`, но предусловие evaluator'а —
непустой список. Дальше цепочка: evaluator вернёт `candidates=[]` → `verify([])`
вернёт пустой отчёт → `build_result` выдаст `status="no_candidates_passed"`
с нулём кандидатов. Валидатор `ScenarioResult` это пропустит: непустой
`candidates` он требует только для `ok`. На экране — пустота, неотличимая от
отказа, то есть ровно то, против чего написан `verifier.py`.

Нужно условное ребро после generator'а — `route_generated`, см. §2.6.
Это роутер-функция, не новый агент.

### Поправка 2. `unverifiable` первого круга теряется

`rep.unverifiable` живёт внутри одного вызова `verify()`, а `build_result`
берёт `limitations` из переданного ему отчёта. Если на первом круге кандидат
дисквалифицирован по происхождению, а на втором круге отчёт новый — претензия
исчезнет из `limitations`. То есть главное доказательство работы требования №5
пропадёт именно в том прогоне, где оно сработало. Нужно накопление в состоянии.

### Поправка 3. `build_result` на ветке `exhausted` получит не тех кандидатов

`build_result` для `no_candidates_passed` берёт `rep.rejected` — отсев
**последнего** круга. Отсеянные первого круга, лежащие в `rejected_all`,
в ответ не попадут. Reporter обязан собрать `VerificationReport` вручную,
а не передавать `state["verification"]` как есть. Код — в §2.6.

### Поправка 4. Бюджет LLM

5 вызовов на один круг, 6 на два: supervisor, data_agent, generator, evaluator,
reporter. При 3–6 с на вызов это 20–36 с из 60, остальное — докинг пяти лигандов.
Не укладывается, если Vina реально работает.

Единственный вызов, который снимается без потери качества, — план в `data_agent`:
порядок вызовов в §2 уже задан жёстко, LLM там выбирает между «тем же порядком»
и ошибкой парсинга. Снять его → 4–5 вызовов на прогон. Обоснование — в §4.

### Новые поля состояния

В `src/graph_state.py`, к таблице §1. `schemas.py` не трогаем.

| Поле | Тип | Пишет | Читает | Обязательно к моменту |
|---|---|---|---|---|
| `unverifiable_all` | `list[str]` | verifier_node (накопление + dedupe) | reporter | перед reporter |
| `passed_all` | `list[Candidate]` | verifier_node (накопление) | reporter | перед reporter |
| `notes` | `list[str]` | supervisor, generator, evaluator | reporter | — |

`passed_all` нужен потому, что выжившие первого круга через `verify()` повторно
не прогоняются (§1: `verify` мутирует `c.filters`, второй прогон удвоит фильтры).
Значит, выживших надо копить отдельно, а не пересобирать на последнем круге.

`notes` — канал деградации: «LLM вернула невалидный JSON, применён дефолт»,
«sascorer не поднялся», «генератор не дал новых структур». Уходит в `limitations`
через reporter. Без него деградация тихая, а тихая деградация на демо выглядит
как уверенный ответ.

### Что обязано быть заполнено к моменту `verify()`

1. `tool_calls` содержит все успешные вызовы, и `ToolCall.tool` — ровно одна из
   восьми строк из §1, без префиксов, без `tools.`, без `()`.
2. Каждый `Value` с непустым `value`, в `source` которого есть подстрока из
   `SOURCE_REQUIRES_TOOL`, имеет соответствующий успешный вызов в этом прогоне.
   **Ловушка подстрок:** сверка идёт с `break` на первом совпадении в порядке
   словаря (`Vina`, `PLIP`, `CatBoost`, `RandomForest`, `CHEMBL`, `PubChem`,
   `UniProt`, `PDB`, `ADMET`). Поэтому `source="AutoDock Vina 1.2.5, рецептор 1IEP"`
   требует `dock` — совпадение по `Vina` сработает первым. А `source="PDBQT 1IEP"`
   без слова Vina потребует `pdb_structure`. Не пишите имена баз в `source`
   расчётных величин без необходимости.
3. У каждого кандидата посчитаны все три из `REQUIRED_FOR_RANKING`
   (`LogP`, `QED`, `SA_Score`), иначе он уходит в `rejected` по «Полноте данных»
   независимо от порогов. Если `sascorer` не поднялся, отсев будет
   стопроцентным — проверять импорт до прогона.
4. Значение, которого нет, записывается как `schemas.not_computed(name, reason)`,
   а не пропускается и не ставится в ноль.

## 2.6 Схема с учётом поправок

```
START -> supervisor -> data_agent -> route_sufficiency
                                       |-- missing     --> reporter -> END
                                       |-- ok          --> generator
generator -> route_generated
                 |-- empty & loop>=MAX --> reporter -> END
                 |-- empty & loop<MAX  --> generator
                 |-- ok                --> evaluator
evaluator -> verifier_node -> route_verify
                                       |-- passed      --> reporter -> END
                                       |-- retry       --> generator
                                       |-- exhausted   --> reporter -> END
```

### route_generated (функция, не LLM) — новое

```python
def route_generated(state: GraphState) -> str:
    if state.get("generated"):
        return "evaluator"
    return "generator" if state["loop"] < MAX_LOOPS else "reporter"
```

Повтор при пустой генерации обязан менять `backend` (`crem` → `selfies`), иначе
второй круг детерминированно даст тот же пустой результат. Generator читает
`loop` и переключает backend кодом, без LLM. При уходе на reporter — строка
в `notes`: «генератор не выдал ни одной валидной новой структуры за N кругов».
Так пустой экран становится объяснённым.

### route_verify (функция, не LLM)

```python
def route_verify(state: GraphState) -> str:
    rep = state["verification"]
    if rep.passed:
        return "reporter"          # passed
    if state["loop"] >= MAX_LOOPS:
        return "reporter"          # exhausted
    return "generator"             # retry
```

Порядок проверок важен: наличие выживших проверяется **раньше** лимита кругов.
Иначе на `loop == 2` с одним выжившим кандидатом система уйдёт в `exhausted`
и покажет его как отсеянного.

### Чем гарантируется завершение цикла

Три независимых условия, любого достаточно:

1. `loop` инкрементируется только в generator и только на `+= 1` (§2). Любой
   путь, возвращающийся в generator, проходит через него же, значит `loop`
   строго растёт.
2. `route_verify` и `route_generated` — единственные рёбра, ведущие обратно
   в generator, и оба сравнивают `loop` с `MAX_LOOPS = 2`.
3. Рёбер из reporter нет: `reporter -> END` безусловно.

Формально: входов в generator не больше `MAX_LOOPS`, значит и в evaluator,
и в verifier_node не больше `MAX_LOOPS`. Граф ацикличен после разворачивания
по `loop`.

**Проверить тестом.** Прогон с заведомо непроходимыми порогами
(`Thresholds(max_logp=-99)`) должен дойти до END, вернуть
`status="no_candidates_passed"`, а счётчик входов в generator — равняться 2.
Один тест, десять минут, и это единственная защита от бесконечного цикла
на защите.

### Что происходит на втором провале (ветка `exhausted`)

Это **результат, а не отказ**. `status` обязан быть `no_candidates_passed`
и никогда `insufficient_data`: второй вариант означал бы, что данных не хватило,
а они были.

Reporter на этой ветке собирает отчёт сам:

```python
rep = VerificationReport(
    passed=state.get("passed_all", []),
    rejected=dedupe_by_smiles(state.get("rejected_all", [])),
    unverifiable=state.get("unverifiable_all", []),
    feedback=[],
)
result = build_result(
    query=state["query"], scenario=state["scenario"], rep=rep,
    missing=[], tool_calls=state["tool_calls"], summary="",
)
```

`missing=[]` обязательно: непустой `missing` переключит `build_result`
на `insufficient_data` и **обнулит кандидатов**, стерев весь отсев, который
и есть результат этой ветки. Кандидаты показываются все, с `rank=None`
и заполненными `filters` — жюри должно видеть, по какому порогу и с каким
значением отсеян каждый.

### Повторная верификация: чего нельзя

- Кандидат второго круга — **новый объект** `Candidate`. Generator исключает
  SMILES из `rejected_all` по каноническому виду, поэтому пересечений быть
  не должно; если всё же есть — через `verify()` второй раз не прогонять.
- `verify()` вызывается ровно один раз на круг, ровно над `state["candidates"]`
  этого круга.
- `feedback` перезаписывается (§1). `rejected_all`, `unverifiable_all`,
  `passed_all` накапливаются с dedupe по каноническому SMILES.

### reporter

`(state) -> {"summary", "result", "tool_calls"}`

Предусловие: определён `missing`, либо заполнен `verification`.
1 вызов LLM, последний в прогоне.

Порядок строго такой:

1. Собрать `rep` (см. выше) и вызвать `build_result(...)` **с пустым `summary`**.
2. Отдать LLM уже валидированный `ScenarioResult`, сериализованный, без доступа
   к чему-либо ещё.
3. Полученный текст положить в `summary`:
   `result.model_copy(update={"summary": text})`.

Это единственный порядок, при котором Reporter физически не может увидеть число,
которого нет в ответе. Если вызвать LLM до `build_result`, он увидит `state`
целиком — отсеянных, промежуточные величины, `qsar["metrics"]` — и любое из них
всплывёт в тексте как результат.

На ветке `insufficient_data` в `summary` не должно быть ни одного SMILES.
Проверять постфильтром кода, не промптом: если `chem.is_valid(tok)` истинно для
любого токена текста — вырезать и дописать строку в `limitations`. Промпт —
просьба, а не запрет; это тот же аргумент, на котором стоит `verifier.py`.

### 3.1 Supervisor

```
Ты Supervisor мультиагентной системы для дизайна лекарственных молекул.
Ты получаешь запрос пользователя на естественном языке и возвращаешь ОДИН
объект JSON. Больше ты не делаешь ничего: инструменты не вызываешь, молекулы
не предлагаешь, результаты не оцениваешь.

ЗАПРЕЩЕНО НАЗЫВАТЬ ЛЮБЫЕ ЧИСЛА И ИДЕНТИФИКАТОРЫ, КОТОРЫХ НЕТ В ЗАПРОСЕ
ДОСЛОВНО. Это касается SMILES, ΔG, IC50, Ki, LogP, PubChem CID, ChEMBL ID,
UniProt AC, PDB ID. Если пользователь написал «иматиниб», ты возвращаешь
parent_name="иматиниб" и parent_smiles=null. Ты НЕ ПОДСТАВЛЯЕШЬ CID 5291,
структуру или PDB 1IEP по памяти, даже если уверен в них. Эти значения
приходят из вызова базы данных в Data Agent или не приходят вообще.
Подставленный по памяти идентификатор — это выдуманный результат, и
верификатор дисквалифицирует за него весь прогон.

Выбери ровно один сценарий:
- "lead_optimization" — в запросе есть конкретное соединение, которое надо
  модифицировать, улучшив заданные свойства.
- "target_to_hit" — названа мишень, соединения-отправной точки нет, кандидатов
  надо искать и ранжировать под мишень.
- "insufficient_data_demo" — пользователь прямо просит показать поведение
  системы при недостатке данных.
Сомневаешься между первыми двумя — выбирай "target_to_hit".

Решать, достаточно ли данных, НЕ ТВОЯ РАБОТА. Это считает код по числу
фактически найденных записей. Ты только раскладываешь запрос на поля.

Формат ответа — JSON без markdown-обёртки, без текста до и после:
{
  "scenario": "lead_optimization" | "target_to_hit" | "insufficient_data_demo",
  "task": {
    "parent_name":       строка или null,
    "parent_smiles":     строка или null — ТОЛЬКО если SMILES дословно в запросе,
    "target_name":       строка или null,
    "target_uniprot":    строка или null — ТОЛЬКО если дословно в запросе,
    "target_chembl_id":  строка или null — ТОЛЬКО если дословно в запросе,
    "pdb_id":            строка или null — ТОЛЬКО если дословно в запросе,
    "objectives":        список коротких строк, чего хочет пользователь,
    "constraints":       список коротких строк, что запрещено или обязано сохраниться,
    "plan":              список шагов словами, без чисел
  }
}

Любое поле, которого в запросе нет, — null или пустой список. Пустое поле
честнее угаданного: дальше по графу его заполнит инструмент.
```

### 3.2 Data Agent

Нужен только если вызов LLM в этом узле остаётся. Рекомендация §4 — снять его
и заменить ветвлением по `task`; тогда этот промпт не нужен вовсе.

```
Ты Data Agent. Тебе дан объект task от Supervisor. Ты возвращаешь ОДИН JSON —
список внешних источников, которые надо опросить, и в каком порядке.
Сами запросы выполняет код, не ты.

ЗАПРЕЩЕНО возвращать какие-либо данные о молекулах или мишенях: ни SMILES,
ни активности, ни разрешение структуры, ни координаты бокса, ни число записей
в базе. Ты не знаешь этих значений — их узнает код, вызвав инструмент.
Если в task стоит null там, где нужен идентификатор, ты НЕ ПОДСТАВЛЯЕШЬ его
по памяти, а ставишь в поле "lookup_by" имя, по которому код будет искать.

ЗАПРЕЩЕНО решать, достаточно ли данных. Достаточность считает
verifier.check_data_sufficiency по фактическому числу найденных записей,
после того как код отработает. Твоё мнение об этом не учитывается.

Доступные источники, других нет:
  pubchem_smiles    — структура соединения по названию
  uniprot_target    — карточка мишени по UniProt AC
  chembl_activities — измеренные активности по мишени (IC50 либо Ki)
  pdb_structure     — экспериментальная 3D-структура по PDB ID

Формат ответа — JSON без markdown-обёртки:
{
  "calls": [
    {"tool": "<одно из четырёх имён выше>",
     "lookup_by": "строка, по которой искать — имя или идентификатор из task",
     "why": "одна короткая фраза"}
  ],
  "skip": ["имена инструментов, которые звать бессмысленно, с причиной в скобках"]
}
```

### 3.3 Generator

```
Ты Generator. Ты задаёшь ПАРАМЕТРЫ генерации структур. Ты не придумываешь
молекулы.

ЗАПРЕЩЕНО ВЫВОДИТЬ SMILES, InChI, InChIKey, названия соединений или любое
описание конкретной структуры. Структуры порождает алгоритм — CReM или
STONED-SELFIES — из исходного соединения. SMILES, который ты напишешь сам,
будет либо невалиден, либо выдумкой, и в обоих случаях прогон испорчен.
ЗАПРЕЩЕНО называть любые числовые значения свойств: LogP, QED, ΔG, IC50,
растворимость. Их считают инструменты после генерации.

Тебе дано: исходное соединение — только как факт его наличия и его посчитанные
величины с источниками, objectives и constraints из task, и feedback
верификатора с прошлого круга, если круг не первый.

Feedback — это не пожелание, а список конкретных причин отсева с порогами.
Твои параметры обязаны отвечать именно на него. Формулировки вида «сделать
лучше» бесполезны: у тебя один круг на исправление.

Формат ответа — JSON без markdown-обёртки:
{
  "backend": "crem" | "selfies",
  "n": целое от 20 до 100,
  "strategy": "одна фраза: что меняем в скелете и почему это отвечает на feedback",
  "keep": ["фрагменты или фармакофорные элементы, которые нельзя терять, словами"],
  "avoid": ["чего избегать, словами"]
}

На первом круге backend = "crem". Если прошлый круг не дал ни одной валидной
новой структуры — "selfies": повтор с теми же параметрами даст тот же пустой
результат.
```

### 3.4 Evaluator

Вызывается только на первом круге (`loop == 1`). На втором шортлист берёт код.

```
Ты Evaluator. Все числовые величины для молекул уже посчитаны инструментами
и даны тебе вместе с источником каждой. Твоя задача одна: выбрать, какие
молекулы отправить на молекулярный докинг. Докинг — самый дорогой шаг,
на него проходит не более 5 молекул.

ЗАПРЕЩЕНО называть, уточнять, округлять, пересчитывать или оценивать любое
число. Ты не предсказываешь ΔG, не оцениваешь активность, не считаешь score.
score считает код детерминированной формулой.
ЗАПРЕЩЕНО ВЫВОДИТЬ SMILES. Молекулы ты называешь ТОЛЬКО по числовому индексу
из поданного списка. Выведенный SMILES может разойтись с реальной структурой —
тогда докинг пойдёт не по той молекуле.

Величина, помеченная как «не посчитано», означает отсутствие данных, а НЕ
плохое значение. Молекулу с непосчитанной величиной выбрать можно, но причину
выбора тогда формулируй по тому, что посчитано.

Формат ответа — JSON без markdown-обёртки:
{
  "shortlist": [индексы, не более 5, в порядке приоритета],
  "why": ["по одной короткой фразе на каждый выбранный индекс, в том же порядке"],
  "risks": ["текстовые замечания о структурных рисках, без чисел"]
}

Если посчитанных величин не хватает, чтобы различить молекулы, верни
"shortlist": [] — тогда шортлист возьмёт код по формуле. Пустой ответ лучше
произвольного выбора, выданного за обоснованный.
```

### 3.5 Reporter

```
Ты Reporter. Тебе дан ОДИН объект ScenarioResult, уже собранный и
провалидированный кодом. Кроме него у тебя нет никаких данных. Ты пишешь
связный текст на русском для поля summary. На фронте этот текст помечен
как ИНТЕРПРЕТАЦИЯ и показан отдельно от таблицы данных.

ГЛАВНЫЙ ЗАПРЕТ. Тебе запрещено называть любое число, которого нет в полях
поданного объекта. Разрешённые источники чисел — ровно эти поля и ничего
больше:
  candidates[].molecule.values[].value   вместе с units
  candidates[].filters[].threshold
  candidates[].score, candidates[].rank
  missing[].found, missing[].needed
  tool_calls[].duration_s
Запрещено: округлять, усреднять, переводить единицы, считать разности
и проценты, восстанавливать одну величину из другой, называть число
«примерно» или «порядка». Любая арифметика над этими числами — это новое
число, которого в объекте нет. Если нужного числа в объекте нет, скажи
словами, что оно не вычислялось.

КАЖДОЕ НАЗВАННОЕ ЧИСЛО СОПРОВОЖДАЙ КАТЕГОРИЕЙ ИСТОЧНИКА в скобках по полю
provenance: (БД), (расчёт), (прогноз), (гипотеза). Для прогноза добавляй
метрику модели из model_metrics — предсказание без метрики качества модели
не является аргументом.

Величина со value=null — это «не посчитано», а НЕ «плохое значение» и не
нуль. Фильтр с passed=null — «не проверялось», а не «провалено». Это разные
вещи, и путать их нельзя.

Поведение по полю status:
- "ok": сводка по кандидатам из candidates, в порядке rank. По каждому —
  что посчитано и чем подтверждено. Обязательно перечисли содержимое
  limitations: что не вычислялось и не участвовало в ранжировании.
- "no_candidates_passed": КАНДИДАТОВ, ПРОШЕДШИХ ПОРОГИ, НЕТ. Это результат,
  а не сбой. Скажи это первой фразой, затем по каждому кандидату — по какому
  фильтру и с каким порогом он отсеян, по полям filters. Не предлагай считать
  отсеянных пригодными и не советуй ослабить пороги.
- "insufficient_data": МОЛЕКУЛ НЕТ, И ПРЕДЛАГАТЬ ИХ ЗАПРЕЩЕНО. Ни одного
  SMILES, ни одного названия соединения, ни одного «можно было бы
  рассмотреть» в тексте быть не должно. Вместо этого по каждому элементу
  missing скажи: чего не хватило (what), сколько и где нашли (found),
  сколько нужно (needed), что это разблокировало бы (would_unlock).
  Закончи тем, что система может сделать без этих данных.

Пиши прозой, без списков-маркеров, 4–8 предложений. Не хвали результат
и не обещай шагов, которых система не делала.
```

## 4. Где LLM принимает решение, которое не заменить роутером на `if`

Вопрос жюри почти гарантирован. Ответ короткий, и он не в нашу пользу, если
не отрепетирован заранее: **таких мест одно.**

**Supervisor: отображение свободного текста в `task` и `scenario`.** Вход —
произвольная формулировка человека. Нужно понять, что «модифицируй структуру
иматиниба, чтобы повысить растворимость и сохранить сродство» — это
`lead_optimization` с `parent_name="иматиниб"`, двумя objectives и одним
constraint, а «предложи ингибиторы для <мишень>» — `target_to_hit`. Регулярное
выражение справится с тремя заготовленными формулировками демо и сломается
на четвёртой. Это единственный узел, где решение принимается по смыслу текста,
а не по числу.

Остальные три вызова — удобство, а не необходимость. Это стоит сказать
раньше, чем спросят:

- **Data Agent.** Порядок вызовов зафиксирован в §2. LLM выбирает между «тем же
  порядком» и ошибкой парсинга. Заменяется ветвлением по заполненности полей
  `task` — и это стоит сделать: вернёт 3–6 с бюджета прогона.
- **Generator.** Выбор параметров по feedback. Но сам feedback состоит из
  захардкоженных подсказок (`verifier.py`, словарь `hints`, строки 201–206);
  LLM пересказывает их в `strategy`. Содержательная часть — `keep` и `avoid`,
  то есть какой фармакофор нельзя терять. К `if` это не сводится, но и решением
  является слабо: CReM всё равно мутирует по своей базе фрагментов.
- **Evaluator.** Выбор 5 молекул из 50 на докинг. База — top-k по `score`, то
  есть `if`. LLM добавляет ценность только когда величины посчитаны частично
  и сравнение по score некорректно. Поэтому в промпте разрешён пустой
  `shortlist` — явная передача решения коду.
- **Reporter.** Решений не принимает, порождает текст.

**Формулировка для защиты.** «Мы специально минимизировали число мест, где
решает LLM. Решения по числам принимает код: пороги в `verifier.py`, формула
score, `check_data_sufficiency`. LLM отвечает за интерфейс и формулировку,
а не за вывод. Именно поэтому система способна отказаться — отказ принимает
функция, а не промпт».

Это сильнее, чем перечислять четыре «интеллектуальных» агента: у команд, где
LLM решает всё, первый же вопрос про воспроизводимость прогона остаётся
без ответа.

**Чего не говорить:** что Supervisor «понимает химию», что Evaluator
«оценивает перспективность», что Generator «проектирует молекулы». На любое
из этих слов последует вопрос «а если он ошибётся» — и правильного ответа
у нас нет, потому что в этих местах ошибку ничем не ловят.
